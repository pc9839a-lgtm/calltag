자체 홈페이지·예약·신청 시스템에서 문의가 생겼을 때 Webhook으로 CRM에 전달할 수 있습니다. 하지만 실제 운영에서는 어떤 이벤트를 보낼지, 어떤 필드를 받을지, 중복과 실패를 어떻게 처리할지까지 정해야 안정적으로 쓸 수 있습니다.

먼저 결론

Webhook은 이벤트가 생겼을 때 데이터를 보내는 연결 방식이고, API는 필요할 때 데이터를 요청·생성·수정하는 더 넓은 통신 방식입니다. 외부 문의를 CRM으로 넘기려면 Webhook만 연결하는 것보다 이벤트·필드·중복·오류 처리까지 같이 봐야 합니다.

‘Webhook CRM 연동’ 검색에는 5가지 요구가 섞여 있습니다

지금 필요한 것확인할 항목
자체 문의폼을 CRM으로 보내고 싶음Inbound Webhook·문의 수신
CRM의 상태 변화를 다른 서비스로 보내고 싶음Outbound Webhook·이벤트 전송
필요할 때 고객 데이터를 조회·수정하고 싶음REST API
여러 서비스를 조건부로 연결하고 싶음자동화 플랫폼·중계 서버
문의 이후 상담·재연락까지 관리하고 싶음CRM·고객관리 앱

Webhook을 API와 같은 뜻으로 보면 연동 설계가 꼬이기 쉽습니다. 이벤트가 발생했을 때 데이터를 밀어주는지, 필요할 때 시스템이 직접 조회하는지부터 구분해야 합니다.

Webhook과 API는 호출 방향과 시점이 다릅니다

구분WebhookAPI
작동 시점이벤트 발생 시 전송필요할 때 요청
대표 용도새 문의·예약·상태 변경 알림고객 조회·등록·수정

실제 CRM 연동에서는 새 문의가 생겼다는 사실은 Webhook으로 보내고, 필요하면 API로 추가 정보를 조회하는 식으로 함께 사용할 수도 있습니다.

Webhook 연동이 특히 필요한 상황

01자체 홈페이지 문의폼 — 별도 사이트 문의를 CRM으로 전달
02예약·상담 신청 — 신청 완료 이벤트를 고객관리로 연결
03사내 시스템 — 기존 시스템의 신규 리드를 후속관리로 전달
04외부 플랫폼 — 기본 연동 목록에 없는 서비스 문의 연결
05상태 변화 알림 — CRM의 특정 이벤트를 다른 시스템에 전달

Meta Lead Ads, Google Forms, PageRo처럼 이미 연결 채널이 정해져 있다면 전용 연동을 먼저 보는 편이 쉽습니다. Webhook은 그 밖의 자체 시스템이나 별도 서비스 연결에서 의미가 커집니다.

먼저 ‘어떤 데이터를 보낼지’부터 정하세요

Webhook은 보통 이벤트가 발생했을 때 구조화된 데이터를 전달합니다. CRM 문의 연동이라면 다음처럼 최소한의 필드를 먼저 정하는 편이 좋습니다.

필드역할
external_id외부 시스템의 문의 ID·중복 판단 후보
name고객 식별
phone / email연락 및 중복 판단 후보
source문의가 들어온 서비스·페이지
message최초 문의 내용
created_at문의 발생 시각

실제 콜태그 Webhook에서 지원하는 필드명과 형식은 구현 설정을 기준으로 확인해야 합니다. 위 표는 일반적인 연동 설계 예시이며 콜태그의 고정 API 스키마를 의미하지 않습니다.

외부 필드와 CRM 필드의 매핑을 먼저 정해야 합니다

외부 서비스의 customer_name이 CRM에서는 이름인지, memo인지, 문의 본문인지 애매하면 데이터가 들어와도 실제 업무에 쓰기 어렵습니다.

외부 데이터CRM에서의 역할확인 포인트
이름고객명빈 값 허용 여부
전화번호연락처국가번호·하이픈 처리
문의 유형초기 상태·태그 후보허용값 정의
문의 내용첫 상담 참고길이·특수문자
외부 ID중복·추적용 키 후보유일성 여부

연동 전에 테스트 payload 한 건을 기준으로 실제 저장 결과를 확인하면 필드가 뒤바뀌는 오류를 줄일 수 있습니다.

Webhook은 ‘한 번만 온다’고 가정하면 안 됩니다

네트워크 오류나 재시도 로직 때문에 같은 이벤트가 다시 전송될 수 있습니다. 따라서 가능한 경우 외부 문의 ID, 이벤트 ID, 요청 고유값처럼 같은 요청인지 판단할 기준을 두는 편이 좋습니다.

운영 테스트

같은 요청 2번 전송 · 전화번호만 같은 다른 문의 · 외부 ID가 없는 요청 · 필수값이 빠진 요청을 각각 보내고 새 고객 생성인지 업데이트인지 실제 동작을 확인하세요.

콜태그가 어떤 값으로 중복을 판단하는지는 연동 구현 설정을 기준으로 확인해야 하며, 이 페이지에서 임의의 중복 처리 방식을 보장하지 않습니다.

수신 시스템의 응답코드와 오류 로그도 봐야 합니다

Webhook은 데이터를 보냈다고 끝나는 게 아닙니다. 받는 시스템이 성공 응답을 반환했는지, 필드 검증 오류가 있었는지, 인증이 실패했는지 확인할 수 있어야 문제를 찾기 쉽습니다.

01외부 시스템에서 이벤트 발생
02Webhook 요청 전송
03수신 시스템에서 데이터 검증
04성공·오류 응답 반환
05실패 시 재시도 또는 운영자 확인

연동 도구마다 재시도 정책과 로그 제공 범위는 다릅니다. 운영 전 실제 실패 요청을 만들어 확인하는 편이 안전합니다.

Webhook 보안은 URL만 숨기는 것으로 끝나지 않습니다

Webhook URL이 외부에서 접근 가능한 엔드포인트라면 전송 주체를 확인할 수 있는 인증 방식이 필요할 수 있습니다. 제공 서비스가 지원한다면 서명 검증, 비밀 토큰, Authorization 헤더 같은 방식을 검토하세요.

확인 항목이유
HTTPS전송 구간 보호
토큰·서명 검증정상 발신 요청인지 확인
최소 데이터 전송불필요한 개인정보 전달 방지
로그 마스킹로그에 연락처·개인정보 과다 노출 방지
키 교체·폐기노출 시 기존 인증값 무효화

구체적인 인증·서명 방식은 보내는 서비스와 받는 시스템이 실제로 지원하는 기능을 기준으로 적용해야 합니다.

Webhook 수신 이후부터는 다시 고객관리 문제입니다

이름과 연락처가 정상적으로 들어왔다고 영업이 끝나는 것은 아닙니다.

문의외부 서비스에서 신규 문의 수신
연락첫 통화·문자 등 실제 응대
상담고객 조건·요구사항 기록
행동자료·견적·예약·방문 등 다음 업무
일정고객과 합의한 날짜에 재연락

콜태그는 이 후반부의 고객 상태·상담 기록·다음 할 일·재연락 일정 관리에 초점을 둡니다.

콜태그의 Webhook은 ‘기본 채널 밖의 외부 문의’를 연결할 때 봅니다

Meta Lead Ads, Google Forms, PageRo처럼 이미 구체적인 채널이 있다면 해당 연동 가이드를 먼저 보는 편이 쉽습니다. Webhook은 자체 홈페이지, 예약 시스템, 신청 도구, 사내 서비스처럼 별도 채널을 콜태그 고객관리 흐름에 연결할 때 검토할 수 있습니다.

모든 Webhook 요청이 조건 없이 즉시 확정 고객으로 등록되고 이후 업무까지 자동 결정된다고 설명하지 않습니다. 실제 수신 방식과 지원 필드는 구현 설정에 따라 달라질 수 있고, 상담 결과와 다음 행동은 실제 업무에 맞게 관리해야 합니다.

Webhook CRM 연동에 대해 자주 묻는 질문

Webhook과 API는 무엇이 다른가요?

Webhook은 특정 이벤트가 발생했을 때 한 시스템이 다른 시스템의 URL로 데이터를 보내는 방식이고, API는 필요할 때 데이터를 요청하거나 생성·수정하는 더 넓은 통신 방식입니다. 실제 연동에서는 둘을 함께 쓰는 경우도 있습니다.

Webhook으로 외부 문의를 콜태그에 연결할 수 있나요?

Webhook 기반으로 외부 서비스의 문의를 콜태그 고객관리 흐름에 연결할 수 있습니다. 실제 지원 필드, 수신 방식과 시점은 연동 설정과 서비스 상태에 따라 달라질 수 있습니다.

Webhook을 연결하면 모든 문의가 자동으로 고객이 되나요?

그렇게 단정하면 정확하지 않습니다. Webhook은 외부 이벤트와 데이터를 전달하는 연결 방식이고, 실제 고객 상태·상담 결과·다음 행동은 업무 흐름에 맞춰 확인하고 관리해야 합니다.

Webhook 연동에서 가장 먼저 테스트할 것은 무엇인가요?

테스트 문의 한 건을 보내 수신 여부, 필수 필드, 데이터 형식, 중복 처리, 오류 응답을 확인하는 것이 좋습니다. 같은 요청이 두 번 들어오는 상황도 함께 테스트하면 운영 오류를 줄일 수 있습니다.

같은 Webhook이 여러 번 들어오면 어떻게 해야 하나요?

연동 구조에 따라 동일 이벤트가 재전송될 수 있으므로 가능하면 이벤트 ID나 외부 문의 ID처럼 중복 판단에 사용할 값을 두는 편이 좋습니다. 실제 콜태그 연동에서 어떤 값으로 중복을 처리하는지는 구현 설정을 확인해야 합니다.

Webhook 보안에서 무엇을 확인해야 하나요?

HTTPS 사용, 인증 토큰이나 서명 검증 지원 여부, 민감정보 최소 전송, 로그에 개인정보를 과도하게 남기지 않는지 등을 확인하는 것이 좋습니다. 구체적인 인증 방식은 보내는 서비스와 받는 시스템의 구현에 따라 다릅니다.

일반 사용자도 Webhook을 써야 하나요?

대부분은 아닙니다. Meta Lead Ads, Google Forms, PageRo처럼 이미 연결할 채널이 정해져 있다면 해당 연동을 먼저 보는 편이 쉽습니다. Webhook은 자체 홈페이지나 예약·신청 시스템처럼 별도 채널을 연결할 때 의미가 큽니다.

외부 문의를 매번 옮겨 적고 있다면 연결부터 확인해보세요.
