# 페이지로 고객문의 → 콜태그 앱 연동

기준 버전: **콜태그 Android 0.39.0**  
기준일: **2026-08-02**  
요구사항 갱신일: **2026-08-13**  
요구사항 검토 기준 브랜치: **agent/calltag-v04422-billing-live**

## 1. 현재 운영 구조

페이지로와 콜태그는 같은 Inlet 계정의 `ownerId`를 기준으로 연결한다. 일반 사용자가 Webhook 주소, 비밀키, workspace 키를 직접 입력하지 않는다.

```text
페이지로 공개 랜딩에서 문의 접수
→ POST /api/leads 저장 성공
→ PageRo 미들웨어가 같은 D1의 CallTag 문의 큐에 복제
→ 문의 소유 프로젝트의 owner_id 저장
→ 콜태그 앱 로그인 세션 검증
→ 같은 ownerId 문의만 앱으로 전달
→ 로컬 고객 생성 또는 기존 고객 갱신
→ 서버에 IMPORTED ACK
```

운영 큐 상태 확인:

```text
GET https://pagero.kr/api/call/pagero/health
```

정상 응답:

```json
{
  "ok": true,
  "service": "pagero-calltag-lead-queue",
  "database": "ready"
}
```

## 2. 일반 사용자 연결 방법

별도 연동키를 발급하거나 붙여넣지 않는다.

1. 페이지로에 사용할 이메일 계정으로 로그인한다.
2. 콜태그 앱에도 **동일한 계정**으로 로그인한다.
3. 페이지로에서 랜딩페이지를 만들고 공개한다.
4. 공개 랜딩페이지에서 고객 문의가 접수되면 문의가 자동으로 콜태그 전달 대기열에 들어간다.
5. 콜태그 앱에서 `더보기 → 페이지로 연결 → 지금 동기화`를 누른다.
6. 신규 고객 수와 기존 고객 갱신 수를 확인한 뒤 고객목록으로 돌아간다.

앱의 `페이지로 연결` 화면에는 다음 정보가 보인다.

- 현재 콜태그 로그인 이메일
- 자동 연결 준비 여부
- 마지막 동기화 시간
- 신규 고객 수
- 기존 고객 갱신 수
- 확인이 필요한 문의 수
- 마지막 오류 메시지와 오류 코드
- 페이지로 열기
- 지금 동기화

계정이 다르면 문의가 보이지 않는다. 콜태그에서 로그아웃한 뒤 페이지로와 같은 계정으로 다시 로그인해야 한다.

## 3. 테스트 계정

현재 연동 테스트 계정:

```text
pc9839a@naver.com
```

테스트 조건:

```text
페이지로 프로젝트 소유 계정 = pc9839a@naver.com
콜태그 앱 로그인 계정       = pc9839a@naver.com
```

테스트 문의는 기존 고객과 구분하기 위해 아직 콜태그에 없는 전화번호를 사용한다.

권장 테스트값:

```text
이름: 페이지로 연동 테스트
문의내용: 콜태그 자동등록 테스트 2026-08-02
전화번호: 앱에서 확인 가능한 미등록 테스트 번호
```

테스트 순서:

1. `pc9839a@naver.com` 소유의 페이지로 랜딩을 공개한다.
2. 공개 페이지에서 테스트 문의 1건을 접수한다.
3. 콜태그 0.39.0 앱을 `pc9839a@naver.com`으로 로그인한다.
4. `더보기 → 페이지로 연결`로 이동한다.
5. 화면의 연결 계정이 `pc9839a@naver.com`인지 확인한다.
6. `지금 동기화`를 누른다.
7. `신규 1건` 또는 `기존 고객 갱신 1건` 결과를 확인한다.
8. 뒤로 이동한 뒤 고객목록에서 `[페이지로]` 문의 메모와 유입 배지를 확인한다.

## 4. 서버 API

### 앱 문의 조회

```text
GET /api/call/pagero/leads?after=0&limit=50
X-Inlet-Session: <콜태그 로그인 세션>
```

서버는 세션에서 `ownerId`를 확인하고 해당 소유자의 `PENDING`, `DELIVERED` 문의만 반환한다.

### 앱 처리 완료

```text
POST /api/call/pagero/leads/ack
X-Inlet-Session: <콜태그 로그인 세션>
Content-Type: application/json
```

```json
{
  "leadIds": [1, 2],
  "status": "IMPORTED",
  "result": "신규 고객 1건, 기존 고객 갱신 1건"
}
```

지원 상태:

- `PENDING`: 페이지로 문의 저장 완료
- `DELIVERED`: 앱에 전달했지만 ACK 전
- `IMPORTED`: 앱 고객 DB 반영 완료
- `REJECTED`: 번호 오류 등 앱 반영 불가

## 5. Android 동작

주요 파일:

```text
PageroLeadApiClient.java
PageroLeadSyncManager.java
PageroLead.java
PageroLeadReceiptStore.java
PageroConnectionActivity.java
PageroConnectionStatusStore.java
CustomerSourceResolver.java
```

Android 처리 순서:

1. 운영 API `https://pagero.kr/api/call/pagero/leads`를 우선 호출한다.
2. 문의 전화번호로 기존 고객을 조회한다.
3. 고객이 없으면 `source=페이지로` 신규 고객을 만든다.
4. 같은 번호가 있으면 고객을 중복 생성하지 않고 기존 고객을 갱신한다.
5. 문의내용, 랜딩 ID, 캠페인, 접수 URL을 고객 메모에 추가한다.
6. `PAGERO_INQUIRY` interaction을 기록한다.
7. 로컬 `event_id` 수신 이력으로 중복 반영을 막는다.
8. 고객 저장 후 서버에 `IMPORTED` ACK를 보낸다.
9. 동기화 성공 여부와 건수를 앱 화면에 저장·표시한다.

자동 동기화 시점:

- 앱 프로세스 시작
- 보호된 앱 화면 재진입
- `페이지로 연결` 화면에서 `지금 동기화` 실행

현재는 앱이 완전히 종료된 상태에서 FCM Push로 문의를 즉시 알리는 방식이 아니다. 앱을 열거나 `지금 동기화`를 실행해야 한다.

## 6. 서버 구현 위치

페이지로 저장소 `pc9839a-lgtm/inlet`:

```text
functions/api/_middleware.js
functions/api/call/pagero/_shared.js
functions/api/call/pagero/leads.js
functions/api/call/pagero/leads/ack.js
functions/api/call/pagero/health.js
migrations/0006_calltag_pagero_lead_queue.sql
```

페이지로 `/api/leads` 저장이 성공한 경우에만 CallTag 큐에 복제한다. 큐 복제가 실패해도 기존 페이지로 문의 접수 자체는 실패시키지 않는다.

## 7. 보안·데이터 원칙

- 일반 사용자에게 서버 비밀키를 노출하지 않는다.
- 이메일 문자열을 직접 고객 조회 조건으로 사용하지 않는다.
- PageRo 프로젝트 소유자의 `owner_id`와 CallTag 로그인 세션의 `ownerId`를 사용한다.
- 모든 조회와 ACK에 `ownerId` 조건을 적용한다.
- `event_id` UNIQUE 제약과 Android 수신 이력으로 중복을 이중 차단한다.
- 고객 저장이 성공하기 전에는 `IMPORTED` ACK를 보내지 않는다.
- 잘못된 전화번호는 `REJECTED` 처리한다.
- 기존 고객·문의 데이터를 초기화하지 않는다.

## 8. 현재 제한과 후속 개선

- 앱 종료 상태의 즉시 Push 알림은 아직 없다.
- 문의 동기화는 한 번에 최대 200건이다.
- 동일 번호 기존 고객은 새 고객을 만들지 않고 기존 고객을 갱신한다.
- 현재 고객의 `source`는 페이지로 문의가 들어오면 `페이지로`로 갱신된다. 장기적으로는 `최초 유입 경로`와 `최근 문의 경로`를 별도 필드로 분리해야 한다.
- 실기기 E2E 검증 전에는 운영 연동 완료로 기록하지 않는다.

# 2026-08-13 페이지로 × 콜태그 개선 요구사항

이 섹션은 기존 연동 구조를 폐기하는 문서가 아니라, 현재 `agent/calltag-v04422-billing-live` 코드 기준으로 확인된 문제와 다음 구현 요구사항을 정의한다.

**중요: 이 문서 갱신에서는 앱/서버 코드를 수정하지 않았다. 구현 명세만 확정한다.**

## 9. 페이지로 문의 데이터 전체 전달

### 9.1 현재 확인된 문제

현재 서버 연동 계층은 다음 데이터를 저장·반환할 수 있다.

- 고객명
- 전화번호
- 이메일
- 문의내용
- 페이지/사이트 ID
- 캠페인
- 접수 URL
- 접수시각
- `metadata`

하지만 현재 Android `PageroLead` 모델은 서버가 반환하는 `metadata`를 읽지 않는다.

Android에서는 현재 문의를 다음 중심으로 메모화한다.

```text
[페이지로]
문의내용
랜딩페이지: <siteId>
캠페인: <campaign>
접수 URL: <sourceUrl>
```

따라서 페이지로 입력폼의 개별 질문/답변이 `metadata` 또는 별도 동적 필드에 존재하는 경우, 서버까지는 전달되더라도 콜태그 앱에서 누락될 수 있다.

### 9.2 목표

페이지로에서 고객이 실제로 입력한 **문의 항목 전체를 콜태그가 보존하고 표시**해야 한다.

유입정보보다 고객의 실제 답변을 우선한다.

표시 우선순위:

```text
1. 고객 기본정보
2. 문의 질문/답변 전체
3. 문의내용
4. 접수일시
5. 페이지명/페이지 ID
6. 캠페인
7. 접수 URL
```

`페이지 ID`, `캠페인`, `접수 URL` 같은 추적정보는 고객 응대의 핵심 내용보다 아래에 배치하거나 접어서 표시한다.

### 9.3 권장 데이터 구조

동적 입력폼은 필드가 늘어나더라도 앱 업데이트 없이 보존할 수 있도록 배열 구조로 전달한다.

```json
{
  "customer": {
    "name": "홍길동",
    "phone": "01012345678",
    "email": "test@example.com"
  },
  "inquiry": {
    "content": "상담 요청합니다.",
    "fields": [
      {
        "id": "field_01",
        "label": "희망 상담 시간",
        "value": "오후 3시 이후",
        "order": 1
      },
      {
        "id": "field_02",
        "label": "관심 서비스",
        "value": "프로 요금제",
        "order": 2
      }
    ]
  }
}
```

원칙:

- 페이지로 폼에 표시된 질문명을 그대로 보존한다.
- 답변 순서를 보존한다.
- 앱이 모르는 신규 필드는 버리지 않는다.
- 알 수 없는 필드는 `추가 문의정보` 영역에 그대로 표시한다.
- 문의 원문은 별도로 보존한다.
- 유입 추적용 정보와 고객 답변을 한 문자열로 억지로 합치지 않는다.

### 9.4 구현 전 추가 확인

실제 페이지로 입력폼 저장/복제 코드가 어떤 값을 `metadata`에 넣는지는 페이지로 송신부 또는 실제 운영 payload를 함께 확인해야 한다.

서버 → Android 구간에서 `metadata`가 현재 유실되는 문제는 확인된 상태다.

## 10. 권한 부족 UX 통일

### 10.1 원칙

사용자가 기능을 눌렀을 때 필요한 Android 권한이 없다면 `권한이 없습니다` 토스트만 보여주고 끝내지 않는다.

항상 다음 흐름으로 처리한다.

```text
기능 실행
→ 필요한 권한 확인
→ 짧은 이유 표시
→ 바로 Android 권한 허용창 또는 해당 시스템 설정 화면 실행
→ 허용 후 원래 기능 재시도 가능
```

### 10.2 권한 종류 구분

#### Android 런타임 권한

예:

- 연락처 읽기
- 전화 상태
- 통화기록
- 문자 발송
- 알림

처리:

`권한 허용` 액션 → Android 시스템 권한창.

`다시 묻지 않음` 상태라 시스템 권한창이 나오지 않는 경우 → 앱 설정의 해당 권한 화면으로 이동한다.

#### 특수 역할/시스템 설정

예:

- 발신자 ID 및 스팸 앱 / Call Screening Role

처리:

해당 Role 요청창 또는 정확한 시스템 설정 화면으로 이동한다.

#### 유료 기능/요금제 이용권

이것은 Android 권한이 아니다.

잘못된 문구:

```text
문자 기능 이용 권한이 필요합니다.
```

권장 문구:

```text
문자 기능을 이용할 수 있는 요금제가 필요합니다.
```

액션:

```text
요금제 보기
```

운영체제 권한과 상품 이용권을 UI에서 절대 같은 `권한`으로 표현하지 않는다.

## 11. 고객목록 빠른 액션 확장

고객목록에서 고객 카드를 열지 않고 다음 동작을 바로 할 수 있어야 한다.

필수 액션:

- `상태 변경`
- `문자 보내기`
- `연락처 저장`
- `삭제`

고객 카드 자체 터치:

- 고객 상세 화면 진입

모바일에서 버튼 4개를 한 줄에 억지로 넣지 않는다. 필요하면 2×2 액션 영역 또는 `더보기`를 사용하되 자주 쓰는 `상태 변경`, `문자 보내기`는 즉시 노출한다.

### 11.1 고객 삭제

삭제는 오작동 방지를 위해 확인 단계를 둔다.

권장 기본:

```text
삭제
→ 확인
→ 고객목록에서 제거
→ 실행 직후 되돌리기 가능
```

CRM 이력, 일정, 문자, 통화 이력이 고객 ID를 참조할 수 있으므로 구현 전에 DB 관계를 확인한다.

기본 삭제는 soft delete를 우선 검토하고, 개인정보 영구삭제가 별도로 필요하면 명확히 구분한다.

### 11.2 연락처 저장

현재 앱 정책은 신규 설치에서 `WRITE_CONTACTS`를 일반 필수권한으로 요구하지 않는 방향이다.

따라서 기본 구현 권장안:

```text
연락처 저장
→ Android 연락처 추가 화면 실행
→ 고객명/전화번호/이메일 자동 입력
→ 사용자가 저장 버튼만 누름
```

장점:

- 불필요한 연락처 쓰기 권한을 요구하지 않는다.
- 삼성/Google 등 실제 연락처 저장 계정을 사용자가 선택할 수 있다.
- 기존 개인정보 안내의 `연락처 내용을 임의로 수정하지 않음` 원칙을 유지하기 쉽다.

진짜 한 번의 터치로 연락처 DB에 직접 삽입하려면 `WRITE_CONTACTS` 권한, 중복 연락처 처리, 저장계정 정책, 개인정보 안내 변경까지 함께 설계해야 한다.

페이지로 유입 표시인 `[페이지로]` 또는 `페이지로` 텍스트를 시스템 연락처 이름에 강제로 붙이지 않는다. 유입경로는 콜태그 내부 배지로 관리한다.

## 12. 홈 전화 기능 UX 정리

현재 홈에는 다음 두 기능이 인접해 있지만 의미가 명확히 구분되지 않는다.

### 통화 감지

의미:

- 수신/발신/부재중 통화를 감지
- 통화 종료 후 고객 이력 연결
- 통화 후 메모/후속업무 처리의 기반 기능

표시 예:

```text
통화 감지
통화가 끝난 뒤 고객기록과 후속업무를 연결합니다.
[사용 중]
```

### 수신 고객정보 표시

의미:

- 전화가 올 때 기존 고객 정보를 화면에 표시
- Call Screening / 발신자 ID 역할과 관련된 별도 기능

표시 예:

```text
수신 전화 고객정보 표시
전화가 올 때 저장된 고객의 이름 · 상태 · 최근 메모를 표시합니다.
[사용 중]
```

### 공통 상태

둘 다 다음 상태가 명확히 보여야 한다.

- `사용 중`
- `사용 안 함`
- `권한 필요`
- `지원 안 됨`

`권한 필요` 상태에서 누르면 설명 토스트만 띄우지 않고 해당 권한/역할 허용 화면으로 즉시 연결한다.

두 항목은 홈에서 `전화 기능` 그룹 안에 묶되 서로 다른 기능임을 텍스트와 상태로 명확히 구분한다.

## 13. 페이지로 문의 고객 문자 발송

### 13.1 구현 가능 여부

**구현 가능.**

현재 콜태그에는 문자 발송, 템플릿, 업무시간, 중복방지, 발송내역, SIM 선택 등에 사용할 수 있는 기존 문자 자동화 구조가 있다.

현재 자동화 트리거는 주로 다음과 같다.

- 수신 통화 종료
- 발신 통화 종료
- 부재중/거절
- 통화 후 지연 발송
- 수동 발송
- 캠페인 발송

페이지로 신규 문의 전용 트리거를 추가하는 방식이 적합하다.

권장 내부 트리거 예:

```text
PAGERO_LEAD_RECEIVED
```

### 13.2 기본 흐름

```text
페이지로 문의 접수
→ 콜태그 문의 동기화
→ 고객 신규 생성 또는 기존 고객 갱신
→ 문의정보 전체 저장
→ 페이지로 문의 이력 생성
→ 자동문자 설정 확인
→ 발송조건 확인
→ 문자 발송
→ 발송상태 저장
→ 사용자 화면 갱신
```

### 13.3 두 가지 발송 방식

#### 수동 즉시 발송

페이지로 문의 알림/고객 카드/상세에서 `문자 보내기`를 누르면 해당 고객 번호로 즉시 작성/발송 흐름에 들어간다.

#### 문의 접수 자동문자

설정에서 사용자가 직접 ON/OFF 한다.

권장 기본값:

```text
OFF
```

설정 예:

- 자동문자 사용 ON/OFF
- 전체 페이지 적용 / 페이지별 적용
- 페이지별 템플릿
- 즉시 발송 / 지연 발송
- 업무시간 적용
- 동일 번호 중복발송 제한
- 사용할 SIM

### 13.4 페이지별 템플릿

페이지로의 각 랜딩페이지 목적에 따라 답장을 다르게 보낼 수 있어야 한다.

예:

```text
웨딩 문의 페이지 → 웨딩 문의 접수 템플릿
보험 상담 페이지 → 보험 상담 접수 템플릿
홈페이지 제작 페이지 → 제작 문의 접수 템플릿
```

지원 권장 변수:

```text
{고객명}
{페이지명}
{문의내용}
{회사명}
{담당자명}
```

예시:

```text
{고객명}님, {페이지명}을 통해 문의가 정상 접수되었습니다.
담당자가 확인 후 연락드리겠습니다.
```

### 13.5 발송 정책

기존 문자 자동화 정책을 재사용한다.

- 문자 기능 이용권 확인
- `SEND_SMS` 권한 확인
- 선택 SIM 확인
- 업무시간 확인
- 발송 제외 대상 확인
- 동일 번호 중복발송 방지
- 템플릿 변수 치환 검증

같은 사람이 짧은 시간에 폼을 여러 번 제출해도 접수문자가 연속으로 반복 발송되지 않도록 한다.

중복방지 기준은 페이지별 또는 트리거별로 관리할 수 있어야 한다.

## 14. 페이지로 문의 문자 발송상태 표시

### 14.1 사용자에게 반드시 보여줄 상태

페이지로 유입 고객에게 접수문자가 실제로 처리되었는지 사용자가 바로 확인할 수 있어야 한다.

사용자 화면 상태는 다음 4개를 기본으로 한다.

| 상태 | 의미 | 사용자 액션 |
|---|---|---|
| `문자 미발송` | 자동문자 OFF, 조건 제외, 아직 발송하지 않음 | `문자 보내기` |
| `문자 발송중` | 발송 작업이 생성되어 처리 중 | 상태 확인 |
| `문자 발송완료` | 휴대폰 문자 발송 요청이 정상 처리됨 | 필요 시 상세 확인 |
| `문자 발송실패` | 권한, SIM, 발송오류 등으로 실패 | `다시 보내기` |

내부 상태가 `SKIPPED`인 경우 사용자에게는 기본적으로 `문자 미발송`으로 표시하고, 상세에서 사유를 제공한다.

예:

```text
문자 미발송
사유: 업무시간 외
```

또는

```text
문자 미발송
사유: 동일 번호 중복발송 제한
```

### 14.2 고객목록 표시

페이지로 유입 고객 카드에서 한눈에 확인할 수 있어야 한다.

예:

```text
김도윤
페이지로 · 신규 문의
문자 발송완료 ✓
```

문자 실패 시:

```text
문자 발송실패
[다시 보내기]
```

색상만으로 상태를 구분하지 않고 텍스트를 반드시 함께 표시한다.

### 14.3 고객 상세 표시

페이지로 문의 블록에 발송 이력을 함께 보여준다.

예:

```text
페이지로 문의
접수       15:02
자동문자   15:02 발송완료
템플릿     문의 접수 안내
```

실패 시:

```text
자동문자   발송실패
사유       문자 발송 권한 필요
[권한 허용] [다시 보내기]
```

요금제 문제라면 `권한 허용`이 아니라 `요금제 보기`를 보여준다.

### 14.4 신규 문의 알림 표시

페이지로 신규 문의 알림에도 가능하면 현재 자동문자 상태를 함께 보여준다.

예:

```text
페이지로 신규 문의
김도윤 · 홈페이지 제작 문의
문자 발송완료 ✓
```

담당자가 알림만 보고도 접수문자 발송 여부를 판단할 수 있게 한다.

### 14.5 발송완료의 정의

`문자 발송완료`는 **SMS 발송 처리가 정상적으로 수행되었다는 의미**다.

이를 다음과 혼동하지 않는다.

- 상대방이 문자를 읽었다.
- 상대방이 실제 화면에서 확인했다.
- 카카오톡처럼 읽음 상태가 확인되었다.

일반 SMS에서 읽음 여부는 보장하지 않으므로 UI에 `읽음` 상태를 임의로 만들지 않는다.

### 14.6 발송 로그

페이지로 자동문자도 기존 콜태그 문자 발송내역에 포함한다.

최소 저장 항목:

- 고객 ID
- 문의/event ID
- 전화번호
- 발송 트리거 `PAGERO_LEAD_RECEIVED`
- 템플릿 ID
- 발송시각
- 상태
- 실패/미발송 사유
- 사용 SIM

동일 문의를 재동기화해도 같은 event ID의 자동문자가 중복 발송되지 않도록 별도 idempotency 기준을 둔다.

## 15. 권장 UI 흐름

최종 사용자 경험은 다음 흐름을 목표로 한다.

```text
페이지로에서 문의 접수
        ↓
콜태그 고객 자동등록/기존고객 갱신
        ↓
문의 질문·답변 전체 표시
        ↓
페이지로 신규 문의 알림
        ↓
자동문자 ON이면 발송
        ↓
문자 발송완료 / 실패 / 미발송 상태 표시
        ↓
사용자가 바로 전화 · 문자 · 상태변경 · 연락처저장
        ↓
콜태그 CRM에서 후속관리
```

핵심 목표는 단순한 `페이지로 문의 가져오기`가 아니다.

```text
온라인 문의 발생
→ 즉시 고객화
→ 접수 사실 자동 안내
→ 발송 여부 확인
→ 바로 연락
→ 후속 관리
```

까지 하나의 끊기지 않는 흐름으로 만드는 것이다.

## 17. 구현 후 필수 검증 시나리오

1. 페이지로 폼에 텍스트, 선택형, 연락처, 이메일 등 여러 필드를 만든다.
2. 테스트 문의를 접수한다.
3. 콜태그에서 모든 질문명과 답변이 순서대로 보이는지 확인한다.
4. 신규 고객 자동문자 OFF 상태에서 `문자 미발송`이 표시되는지 확인한다.
5. 자동문자 ON 상태에서 정상 발송 후 `문자 발송완료`가 표시되는지 확인한다.
6. `SEND_SMS` 권한을 제거하고 문의를 접수해 `문자 발송실패`와 `권한 허용` 동작을 확인한다.
7. 문자 이용권이 없는 계정에서 `요금제 보기`로 연결되는지 확인한다.
8. 같은 전화번호로 짧은 시간에 문의를 두 번 넣어 중복문자 방지 여부를 확인한다.
9. 기존 고객 번호로 문의했을 때 고객이 중복 생성되지 않는지 확인한다.
10. 자동문자 실패 후 `다시 보내기`로 정상 복구되는지 확인한다.
11. 고객목록에서 상태 변경, 문자, 연락처 저장, 삭제 액션을 확인한다.
12. 홈에서 `통화 감지`와 `수신 전화 고객정보 표시`를 사용자가 구분할 수 있는지 확인한다.
